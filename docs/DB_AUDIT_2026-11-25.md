## Executive findings

1. Two active district records exist: Kohat (code 001) and Peshawar (code 002).
2. Both districts have a `district_app_state` JSONB snapshot. Kohat snapshot revision is 12; Peshawar revision is 2.
3. The normalized operational tables currently report zero rows, including DATA hierarchy, staff, trainers, venues, training plans/batches/participants/attendance, assignments and reserve staff.
4. Therefore the JSONB snapshots are the current populated data store. The normalized relational tables are not yet populated and must not be treated as the current source of truth.
5. `district_memberships` has zero rows. `user_profiles` has one row. This means no district-specific memberships have been configured yet; access should be tested with the intended user roles before rollout.
6. Supabase reports no migration records in its migration history table. Existing database changes appear not to be tracked as a formal migration sequence.
7. Security advisor findings need review before production use. Performance advisor also reports 12 unindexed foreign keys and RLS/policy optimization opportunities.

## Security advisor findings

- `public.kpk_safe_bigint(text)` has a mutable search_path warning.
- Public/anon and authenticated execute grants are reported for SECURITY DEFINER functions, including trigger functions `prevent_profile_privilege_changes()` and `prevent_self_global_admin_escalation()`. Review grants and ensure only intended callers can execute RPC-exposed functions.
- Auth leaked-password protection is disabled.
- SECURITY DEFINER helper functions `has_district_access`, `has_district_role`, and `is_global_admin` use a fixed search_path (`pg_catalog, public`) in their definitions; keep their grants and behavior under review.

Do not apply blanket REVOKE statements without checking which functions are called by policies, triggers, and the frontend.

## Performance advisor findings

- 12 foreign keys lack covering indexes.
- RLS policies on profiles/memberships re-evaluate auth expressions per row.
- Multiple permissive policies are reported on district_memberships and districts.
- 12 indexes are reported unused. Do not drop them based only on this finding; the project may not yet have meaningful production query traffic.

## Critical migration risks

1. The live snapshots have fewer DATA entries than the separate Kohat backup (788 vs 1,062).
2. The live Kohat snapshot has empty staff/trainers/venues/rules arrays, while the separate backup has 6,644 staff, 12 trainers, 11 venues, and 18 rules.
3. Live attendance arrays differ (Kohat 5,162 vs backup 12,454). These are not interchangeable without reconciliation.
4. Peshawar snapshot DATA array length is 2,521; do not assume it means polling stations or source rows until the legacy app's data transformation is verified.
5. The existing import RPC `import_district_data_rows` performs upserts into relational DATA tables but does not by itself migrate the other JSONB sections. Its update behavior and repeat-import semantics need tests before use.

## Recommended next sequence

1. Preserve a fresh full backup of both live district snapshots and the authoritative Kohat backup.
2. Inspect the exact legacy app code and snapshot serialization/deserialization paths to identify how the live snapshot became incomplete.
3. Define canonical identity keys for DATA, staff, trainers, venues, attendance, assignments and settings.
4. Build a dry-run migration report: source count, matched count, new count, duplicate candidates, rejected/uncertain rows.
5. Treat the 1,062-row Kohat DATA and 6,644 staff records in the confirmed backup as authoritative; reconcile attendance separately.
6. Only after dry-run verification, migrate one district at a time in a transaction, preserve original snapshots, and verify row counts and business-rule totals.
7. Add versioned SQL migrations to the Git repository and test RLS using global admin, district admin, data entry, training officer and viewer accounts.
